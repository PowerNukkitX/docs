If you are migrating from Mojang's official Bedrock Dedicated Server (BDS), you can retain your worlds and resource packs, but you must manually configure server settings and replace BDS-specific add-ons.

## Step-by-Step Migration

### 1. Set Up PowerNukkitX
Install a fresh PowerNukkitX server. Follow the [Installation](/docs/installation) guide for your operating system. Once installed, run it once to generate configurations and then stop it.

### 2. Migrate Worlds
BDS stores worlds in the `worlds/` directory.
1. Locate your world folder inside the BDS `worlds/` directory (e.g., `worlds/MyBedrockWorld`).
2. Copy this folder into the PowerNukkitX `worlds/` directory.
3. Open `pnx.yml` in your PowerNukkitX server directory and find the `settings` category. Set the `defaultLevelName` to match the exact folder name of your world:
   ```yaml
   settings:
     defaultLevelName: "MyBedrockWorld"
   ```

### 3. Translate Configuration
You must manually copy settings from the BDS `server.properties` file to `pnx.yml`:

| BDS Setting | pnx.yml Category | pnx.yml Key | Description |
| :--- | :--- | :--- | :--- |
| `server-port` | `settings` | `port` | Server UDP Port. |
| `max-players` | `settings` | `maxPlayers` | Max player slots. |
| `online-mode` | `settings` | `xboxAuth` | If `true`, requires Xbox authentication. |
| `allow-list` | `settings` | `allowList` | Enable/disable server whitelist. |
| `gamemode` | `gameplay-settings` | `gamemode` | 0: Survival, 1: Creative, 2: Adventure. |
| `difficulty` | `gameplay-settings` | `difficulty` | 0: Peaceful, 1: Easy, 2: Normal, 3: Hard. |
| `view-distance` | `gameplay-settings` | `viewDistance` | Maximum chunk rendering distance. |

### 4. Migrate Resource Packs
If your BDS server uses resource packs:
1. Locate the `.mcpack` or `.zip` files in BDS `resource_packs/`.
2. Copy them to the PowerNukkitX `resource_packs/` directory.
3. PowerNukkitX will automatically load and offer them to clients when they connect.

## Key Differences & Limitations

### Behavior Packs
- **BDS:** Supports client-side behavior packs containing custom entity logic, component scripts, and animations.
- **PowerNukkitX:** Does **not** support behavior packs. All custom entity, block, and gameplay logic must be handled server-side in Java using PowerNukkitX's robust API or custom plugins. 

### Player Data & Inventories
BDS stores player inventories and locations within the LevelDB world database under player key entries. PowerNukkitX can read standard vanilla player profiles from LevelDB. However, to ensure inventory consistency:
- Back up the `worlds/` directory prior to testing client joins.
- Set `savePlayerData` to `true` in `pnx.yml` (`player-settings`).

## Migrating Add-ons and Scripts

BDS has no plugin system - custom behavior comes from add-ons: JSON-defined blocks and entities, the JavaScript/TypeScript Script API, and `.mcfunction` files. None of these run on PowerNukkitX. Server-side logic must be rebuilt as Java plugins, and JSON content must be re-declared through the registry. The mapping below covers the common cases.

### Script API logic becomes a plugin

A BDS `scriptevent` or event subscription becomes a PowerNukkitX event listener.

```js
// BDS Script API (JavaScript)
import { world } from "@minecraft/server";

world.afterEvents.playerBreakBlock.subscribe((event) => {
    event.player.sendMessage("You broke a block");
});
```

```java
// PowerNukkitX (Java)
import org.powernukkitx.event.EventHandler;
import org.powernukkitx.event.Listener;
import org.powernukkitx.event.block.BlockBreakEvent;

public class MyListener implements Listener {
    @EventHandler
    public void onBreak(BlockBreakEvent event) {
        event.getPlayer().sendMessage("You broke a block");
    }
}
```

Register it in your plugin's `onEnable`:

```java
getServer().getPluginManager().registerEvents(new MyListener(), this);
```

### Custom blocks and entities

BDS defines custom blocks and entities as JSON files inside a behavior pack. PowerNukkitX defines them in Java against its dynamic registry.

```java
@Override
public void onLoad() {
    Registries.BLOCK.registerCustomBlock(this, MyCustomBlock.class);
}
```

Custom blocks implement the `CustomBlock` interface (`org.powernukkitx.block.customblock`), and reference blocks/items by Bedrock string identifier through `BlockID` / `ItemID`. See the [Custom Components](/docs/development/customs) guides for the full API.

### Functions and commands

`.mcfunction` files and command blocks map to real server commands. Register a `Command` (optionally declared with `@CommandDefinition`) on the command map:

```java
getServer().getCommandMap().register("myaddon", new MyCommand());
```

### Resource packs still work

Client-facing resource packs (textures, models, sounds, UI) carry over unchanged - only the server-side behavior needs rebuilding. Copy them into `resource_packs/` as described above.
