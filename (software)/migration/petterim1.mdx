The Nukkit PetteriM1 edition is a Nukkit fork focused on supporting a wide range of Bedrock protocol versions. It keeps Nukkit's Java architecture, config files and world format, so migrating to PowerNukkitX is largely automated.

## Step-by-Step Migration

### 1. Create a Complete Backup
Copy your entire PetteriM1 server directory to a safe location first.

### 2. Update Files
1. Download the latest `powernukkitx.jar` from the [Releases Page](https://github.com/PowerNukkitX/PowerNukkitX/releases).
2. Download a startup script (`start.bat` or `start.sh`) from [PowerNukkitX/scripts](https://github.com/PowerNukkitX/scripts) and place it in the server folder.
3. Replace the old jar with `powernukkitx.jar`. Keep your `nukkit.yml` and `server.properties` in place for now.

### 3. Run the Server
On startup PowerNukkitX detects `nukkit.yml` and `server.properties`, backs them up, converts the settings into `pnx.yml`, and continues booting.

Configuration keys map exactly as in a plain Nukkit migration - see the [Nukkit / Lumi](/docs/migration/nukkit) guide for the full mapping table (`settings`, `gameplay-settings`, `player-settings`).

## World Data
The PetteriM1 edition and PowerNukkitX share the same world format. Your `worlds/` folders load natively without conversion.

## Plugin Compatibility
PetteriM1 edition plugins use the legacy Nukkit API. Simple plugins may run on PowerNukkitX, but anything interacting with block, item or entity registries will break against PowerNukkitX's modern registry system. Prefer PowerNukkitX-native plugin builds, or recompile against the new API.

<Callout type="warning">
    The PetteriM1 edition is built around multi-version support, letting old and new clients join the same server. PowerNukkitX targets a single, current protocol version - clients on older versions may lose access after migrating. Check what versions your players use before switching.
</Callout>

## Migrating Plugin Code

The PetteriM1 edition builds on the classic `cn.nukkit` API. PowerNukkitX moved every class into the `org.powernukkitx` package and modernized several core systems. If you maintain your own plugins, these are the concrete code changes you need to make.

### 1. Update your imports

Every `cn.nukkit` import becomes `org.powernukkitx`. A project-wide find-and-replace of `cn.nukkit` with `org.powernukkitx` covers most of the work.

| Legacy (`cn.nukkit`) | PowerNukkitX (`org.powernukkitx`) |
| --- | --- |
| `cn.nukkit.plugin.PluginBase` | `org.powernukkitx.plugin.PluginBase` |
| `cn.nukkit.Player` | `org.powernukkitx.Player` |
| `cn.nukkit.Server` | `org.powernukkitx.Server` |
| `cn.nukkit.event.*` | `org.powernukkitx.event.*` |
| `cn.nukkit.block.Block` | `org.powernukkitx.block.Block` |
| `cn.nukkit.item.Item` | `org.powernukkitx.item.Item` |
| `cn.nukkit.command.Command` | `org.powernukkitx.command.Command` |

Update your `plugin.yml` too - `main` still points at your main class, but bump `api` to the PowerNukkitX API version (a string, e.g. `"3.0.0"`).

### 2. Numeric IDs become string identifiers

This is the biggest change. Legacy Nukkit addressed blocks and items by numeric ID and meta. PowerNukkitX uses Bedrock's string identifiers exposed through the `BlockID` and `ItemID` constant interfaces.

```java
// PetteriM1 edition - numeric IDs
Block stone = Block.get(Block.STONE);          // int constant
Item sword  = Item.get(Item.DIAMOND_SWORD);    // int constant

// PowerNukkitX - string identifiers
import org.powernukkitx.block.BlockID;
import org.powernukkitx.item.ItemID;

Block stone = Block.get(BlockID.STONE);        // "minecraft:stone"
Item sword  = Item.get(ItemID.DIAMOND_SWORD);  // "minecraft:diamond_sword"
```

Hard-coded numeric IDs will no longer compile - replace them with the matching `BlockID` / `ItemID` constant.

### 3. Block meta gives way to block states

Legacy Nukkit encoded block variants in a numeric meta/damage value. PowerNukkitX represents them as typed block states.

```java
// PetteriM1 edition - meta value
Block wool = Block.get(Block.WOOL, 14); // 14 = red

// PowerNukkitX - block state
Block wool = Block.get(BlockID.RED_WOOL);
```

Move any direct meta-value logic to the block-state API - see the [Block API](/docs/development/customs/blocks) reference.

### 4. Custom content uses the registry

PowerNukkitX replaces static ID tables with a dynamic registry. Register custom content against `Registries` at load time.

```java
@Override
public void onLoad() {
    Registries.BLOCK.registerCustomBlock(this, MyCustomBlock.class);
}
```

Custom blocks implement the `CustomBlock` interface (`org.powernukkitx.block.customblock`). Rebuild them with the [Custom Components](/docs/development/customs) guides.

### 5. Events and commands stay familiar

Implement `Listener`, annotate with `@EventHandler`, register in `onEnable` - only the package moves.

```java
import org.powernukkitx.event.EventHandler;
import org.powernukkitx.event.Listener;
import org.powernukkitx.event.block.BlockBreakEvent;

public class MyListener implements Listener {
    @EventHandler
    public void onBreak(BlockBreakEvent event) {
        event.getPlayer().sendMessage("You broke " + event.getBlock().getName());
    }
}

// register
getServer().getPluginManager().registerEvents(new MyListener(), this);
```

Commands still register through `getServer().getCommandMap()` with the `Command` base class (or the annotation-based `@CommandDefinition`), and scheduling stays on `getServer().getScheduler()`.
